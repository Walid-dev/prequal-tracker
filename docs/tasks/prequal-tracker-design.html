Prequal Tracker design

A subcontractor prequalification tracker with AI response triage. This page explains what was built and why. The step-by-step build, with the outcome of each commit, is the companion page docs/tasks/prequal-tracker-execution-plan.html.

In plain language

A general contractor in Ontario can't let a subcontractor on site until the paperwork is in order. Someone collects the same documents from every electrician, plumber, and HVAC company: a WSIB clearance, a liability insurance certificate, a safety certificate, and for electricians a licence number. They read every answer, and they send it back when something is missing or expired. It's slow, repetitive reading, and a missed expiry date is a real liability.

The tracker turns that into a checklist per subcontractor. Each answer gets an AI triage: a short note that says whether the answer is complete, partial, or insufficient, quotes the exact words behind each problem, and drafts the questions to send back. Hard rules in code check the note before anyone sees it. The reviewer always makes the decision. The AI never accepts anything.

the one-line version

The AI reads, the rules check, the human decides, and every step is saved.

At a glance

  • Type: new feature, a small full-stack app. Build time: about 1 h 45, in four reviewed gates.
  • Problem: reviewers read every subcontractor answer by hand against the request it answers.
  • Approach: a request tracker with one structured AI call per answer, rules in code after the model, and a human decision on every request.
  • Risk: medium. The primary risk is a wrong AI note that a reviewer trusts. Guards: closed lists, quotes that must exist, rules that only make results stricter, and the human decision.
  • Runs with: docker compose up --build. Mock mode by default, so no API key is needed.

How it works

One Next.js server holds the pages, the server actions, and the domain code. The database is a single SQLite file. Only the AI module talks to the outside world, and in mock mode it doesn't.

Walking through it: the reviewer submits a form. A server action validates it with Zod and calls the domain code, which applies the business rules and writes to SQLite. When the reviewer clicks Run AI triage, the triage service loads the latest answer and its request, calls the AI module once, and saves the run, whether it worked or failed. The page then shows the note next to the review buttons.

A request's life

The rules against accepting without a response, and against deciding on an answer that a newer one has replaced, live in requests.ts, not only in the page, so no other caller can skip them. Each case shows its progress (accepted out of total) and lists requests that wait on changes as blockers.

The AI feature: response triage

One triage reads one answer against the request it answers. It's a single structured call to the model, followed by rules in code. The numbers show the order.

1Context

Our rules, the flag definitions, and the request (title, instructions, company, trade, today's date) go in the system instructions. The subcontractor's answer goes alone in the user message, inside <answer> tags, in full up to the form's 20,000-character limit. The prompt says the answer is data, and that any instruction inside it must be reported, never followed.

2One call

One generateText call with a structured output schema, a 30-second timeout, and no tools. Before reading the result, the code checks how the call ended. Only a normal finish counts. A refusal, a cut-off, a content filter, a timeout, a provider error, or any other finish becomes a failed run that says "review by hand". It never becomes a guess.

3Schema

The model must return completeness, a summary, extracted facts (expiry date with the exact words that state it, coverage, holder name), flags from a closed list of six codes (each with a quote), and follow-up questions. The provider gets a strict JSON schema. Our own check lower-cases list values first, because providers don't guarantee their capitalization.

4Rules

Rules in code can only make the result stricter:

  • A flag whose quote isn't in the answer is dropped. The check ignores case, spacing, and curly quotes.
  • An expiry date counts only when the words stating it are in the answer and name that same date (for a range, the latest date). An invalid or unsupported date caps the result at partial and asks for a real date.
  • An expiry date before today adds an "Expired" flag, caps the result at partial, and drafts a question asking for a current document.
  • An answer too long to send in full is capped at partial.
  • Wording that tries to steer the review is flagged and capped at partial. It's flagged for the reviewer, never blocked.
  • Lengths and counts are capped, so the note stays readable. Rule flags come first, then the model's safety flags, so the cap never removes a safety warning.

5Saved run

Every run is saved, ok or failed: the exact input, the model's own completeness, the final result, what the rules changed, the model, the prompt version, tokens, cost, and time. Rows are never edited. One structured log line per run feeds monitoring.

6Reviewer

The note sits next to the review buttons, with the rule changes and the cost in plain view. One click inserts the drafted questions into the note. Accepting or sending back is a human action, recorded with a name and the triage run the reviewer saw.

why one call and not an agent

The model needs exactly two inputs, the request and the answer, and code already has both. A tool loop would add cost, latency, and ways to fail. An agent becomes the right tool when the lookups depend on what the model finds: reading an uploaded certificate only when the text is vague, or checking a public registry only on a near-match. The research behind this design is in docs/research/ai-triage.md.

Decisions

The main ones. Every decision, with why and what was rejected, is in docs/decisions.md.

  • decidedConstruction prequalification. It is a real request-and-response workflow, and Ontario law requires a WSIB clearance from every subcontractor hired directly.
  • decidedOne structured call, no tools. The inputs are known up front, so an agent loop would only add cost and failure modes.
  • decidedRules in code after the model, stricter only. Hard facts like dates and quotes are checked in code, where the model can't talk past them.
  • decidedClaude Sonnet 5 by default. It passed every eval case, at about $0.006 per triage. Haiku 4.5 is a cheaper option through one setting.
  • decidedOne setting picks the model and provider. AI_MODEL=provider:model, through the Vercel AI SDK provider registry. Anthropic and OpenAI are registered.
  • decidedSQLite with Drizzle. Zero setup, migrations as plain SQL in git, and nothing extra in the image.
  • decidedMock mode by default. The app, tests, and CI run with no key and no cost.
  • decidedA human makes every decision. The AI drafts a note. Only a reviewer accepts or sends back.

Tests and checks

  • 51 unit and service tests (Vitest): the workflow rules, the AI rules, every failure path of the triage call with mock models, the triage service, a full case-to-progress flow on a real SQLite database, and the eval scoring.
  • Independent review: a second model (Codex, GPT Sol 6.1) reviewed the whole repo against a written brief, then re-checked each round of fixes. All ten findings were fixed.
  • Browser checks: a headless browser drove the real forms and the triage panel through 19 checks during the build.
  • Docker: the container runs as a non-root user, has no secrets inside, and keeps its data across restarts.
  • CI runs lint, typecheck, tests, the mock eval, the migration check, and the build on every push, with no secrets and no paid calls.

Operations and rollback

  • AI kill switch: set AI_MODE=mock. The tracker keeps working without the AI.
  • Model switch: one setting, AI_MODEL=provider:model, for example anthropic:claude-haiku-4-5 or openai:gpt-6-sol, plus that provider's key. Every run records the model and the prompt version, so results can be compared before and after.
  • Migrations: forward-only SQL files in git. In production they would run as a pre-deploy job, and a bad change is undone with a new migration.
  • Monitoring: one structured log line per triage (status, model, prompt version, tokens, cost, time), ready for a dashboard. Agreement between the AI's completeness and the reviewer's decision is the drift signal, and both are already saved.

Out of scope

Left for next steps, with the reasons in the README: document uploads (where an agent starts to make sense), login and roles, a subcontractor portal with reminders, a public API, browser tests in CI, Postgres, and multiple companies.
